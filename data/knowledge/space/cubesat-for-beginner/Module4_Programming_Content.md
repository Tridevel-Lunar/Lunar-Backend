# Module 4: Programming — Command Your CubeSat
## Lesson Content Reference สำหรับ LAIKA (AI Mentor)

**เป้าหมายของโมดูล:** ผู้เรียนออกจากโมดูลนี้แล้วต้อง (1) เข้าใจว่าดาวเทียมไม่มี "ความคิดเป็นของตัวเอง" ทุกการตัดสินใจต้องมีมนุษย์เขียนโปรแกรมสั่งไว้ล่วงหน้า (2) รู้จักและใช้ concept การเขียนโปรแกรมพื้นฐาน (data type, if/else ซ้อนได้, loop, ตัวแปร/packet, ฟังก์ชัน) ผ่านบล็อก เพื่อสร้างพฤติกรรมที่ซับซ้อนขึ้นเรื่อยๆ ให้ CubeSat ได้ด้วยตัวเอง (3) เห็นผลลัพธ์ของโค้ดตัวเองเป็นภาพจริงบน 3D CubeSat ไม่ใช่แค่ "ถูก/ผิด"

**หลักการสำคัญที่ยึดต่อจากโมดูล 1-3:** ศัพท์เทคนิคทุกตัวต้องมีคำอธิบายกำกับทันทีที่โผล่ครั้งแรก และเนื้อหาต้องแม่นยำเชิงเทคนิค — โมดูลนี้ใช้ block-based programming (การเขียนโปรแกรมแบบต่อบล็อก) เพื่อลดอุปสรรคด้าน syntax แต่ **ตรรกะเบื้องหลังบล็อกต้องสะท้อนหลักการ embedded/protocol จริงที่ใช้ในดาวเทียมจริง** ไม่ใช่ logic ที่แต่งขึ้นเองแบบไม่มีมูล (ดูหัวข้อ 4.6 "เกร็ดเทคนิคเบื้องหลังบล็อก" สำหรับรายละเอียดที่ควรอิงอ้างถูกต้อง)

## 4.1 ทำไมดาวเทียมต้องมีโปรแกรมสั่งงาน

**Hook เปิดเรื่อง:** เปิดด้วยภาพ 3D CubeSat "ลอยนิ่งเฉยๆ" ไม่ทำอะไรเลย
> "ตอนนี้ดาวเทียมดวงนี้เป็นแค่กล่องโลหะราคาแพงที่ลอยอยู่เฉยๆ — มันมี OBC (สมองกลาง) มี EPS มี COMM มี Payload ครบตามที่เรียนในโมดูลที่แล้ว แต่ไม่มีอะไรทำงานเลยสักอย่าง เพราะอะไร?"
> คำตอบ: เพราะ "สมอง" ของมันว่างเปล่า ไม่มีใครบอกมันว่าเจอสถานการณ์แบบไหนต้องทำอะไร ถ้าไม่มีโปรแกรมสั่ง มันจะกลายเป็นแค่ขยะอวกาศ (space debris) ที่ลอยเปะปะไปเรื่อยๆ

**เชื่อมกับโมดูล 2:** ทวนความจำว่า OBC (สมองกลาง) ทำหน้าที่แค่ "รับข้อมูล → ตัดสินใจ → สั่งงาน" — แต่กฎการตัดสินใจทั้งหมดนั้น**มนุษย์ต้องเป็นคนเขียนไว้ล่วงหน้า** OBC ไม่ได้ฉลาดขึ้นมาเอง มันแค่ทำตามเงื่อนไขที่ถูกเขียนสั่งไว้เป๊ะๆ

## 4.2 พื้นฐานที่ต้องรู้ก่อนต่อบล็อก (Foundational Concepts)

ก่อนให้ผู้เรียนลงมือต่อบล็อก ต้องปูพื้น 5 concept นี้ก่อน เพราะ mission ในหัวข้อ 4.4 จะซับซ้อนขึ้นเรื่อยๆ และต้องใช้ concept เหล่านี้จริง ไม่ใช่แค่ if/else เดี่ยวๆ เหมือน draft แรก — ให้สอนแต่ละอันด้วย analogy สั้นๆ ที่ผูกกับดาวเทียมทันที ไม่ใช่สอน programming ลอยๆ แบบทั่วไป

### 4.2.1 Data Type (ชนิดข้อมูล)
ค่าที่ sensor แต่ละตัวอ่านมา "ไม่เหมือนกัน" — ต้องรู้จักก่อนว่าค่าที่ได้เป็นชนิดไหน ถึงจะเอาไปเทียบเงื่อนไขถูก
| ชนิดข้อมูล | หน้าตา | ตัวอย่างจาก sensor ในโมดูล 2 |
|---|---|---|
| **Number (ตัวเลข)** | ค่าตัวเลขที่เอาไปเทียบมากกว่า-น้อยกว่าได้ | `battery level = 45`, `temperature = 32.5` |
| **Boolean (ค่าจริง-เท็จ)** | มีแค่ 2 สถานะ: `true` หรือ `false` | `sun sensor = true`, `in range of ground station = false` |
| **String / Text (ข้อความ)** | ตัวอักษร/ข้อความ | `ground command = "capture_image"` |

**จุดที่ต้องเน้น:** เอา Boolean ไปเทียบแบบ `< 20%` ไม่ได้ (ไม่มี "true น้อยกว่า false") และเอา Number ไปเช็คแบบ `if sun sensor` เฉยๆ ก็ผิด (ต้องเช็คว่า `== true`) — ความผิดพลาดแบบนี้เกิดขึ้นบ่อยกับมือใหม่ ควรมี checkpoint เล็กๆ ให้จับผิดคู่ที่ผิดชนิดข้อมูล

### 4.2.2 If / Else แบบซ้อนได้ (Nested Condition)
ทวนจากที่มีอยู่แล้ว แต่ขยายว่า **if/else ซ้อนกันได้หลายชั้น** ไม่ใช่มีแค่ 2 ทางเลือกเสมอไป เช่น เช็คแบตต่ำมาก (<10%) ก่อน ถ้าไม่ใช่ค่อยเช็คแบตต่ำปานกลาง (<20%) ถ้าไม่ใช่อีกค่อยทำงานปกติ — สื่อสารด้วย diagram แบบ flowchart แตกกิ่งหลายชั้นในบล็อกเอดิเตอร์

### 4.2.3 Loop (การวนซ้ำ)
**Analogy:** OBC ของจริงไม่ได้เช็คค่าแค่ครั้งเดียวจบแล้วหยุด — มันวนเช็ค sensor ซ้ำๆ ตลอดเวลาที่ดาวเทียมยังทำงานอยู่ เหมือนยามเฝ้าประตูที่คอยมองซ้ายขวาซ้ำๆ ไม่ใช่มองแค่ครั้งเดียวแล้วเลิก
- บล็อก `repeat forever` (วนซ้ำตลอดไป) — ครอบ logic ทั้งหมดไว้ข้างใน แทนความจริงที่ว่าโปรแกรมดาวเทียมวิ่งเป็น main loop ต่อเนื่อง
- บล็อก `repeat every [X] seconds` — จำลองการเช็คค่าเป็นรอบๆ (เช่น เช็คแบตทุก 10 วินาที) แทนที่จะเช็คถี่รัวๆ ไม่หยุด

### 4.2.4 การเก็บข้อมูลและ Packet (Variable & Data Packet)
- **Variable (ตัวแปร)** — กล่องเก็บค่าไว้ใช้ทีหลัง เช่น อ่าน `temperature` มาเก็บไว้ในตัวแปรชื่อ `lastTemp` เพื่อเอาไปเทียบกับค่ารอบถัดไปว่าค่าขึ้นหรือลง
- **Packet (แพ็กเก็ตข้อมูล)** — ก่อนส่งข้อมูลลงพื้นโลก (downlink) ต้อง "รวบ" ค่าจาก sensor หลายตัวเข้าเป็นก้อนเดียวก่อนส่ง ไม่ใช่ส่งทีละค่า — บล็อก `pack data [battery, temperature, sun status] → packet` แล้วค่อยเอา packet นั้นไปใส่บล็อก `transmit data`
- **จุดที่ต้องเน้น:** นี่คือเหตุผลที่ดาวเทียมจริงต้องมี telemetry frame/packet format ที่แน่นอน (ทวนแนวคิดจากงานวิจัยจริงเรื่อง protocol ในหัวข้อ 4.6) — ผู้เรียนกำลังทำเวอร์ชันย่อของสิ่งเดียวกัน

### 4.2.5 ฟังก์ชัน (Function)
**Analogy:** แทนที่จะเขียน logic เดิมซ้ำๆ ทุกครั้งที่ต้องเช็คแบต ให้ "ห่อ" มันเป็นฟังก์ชันชื่อ `checkBattery()` ครั้งเดียว แล้วเรียกใช้ซ้ำได้จากตรงไหนก็ได้ในโปรแกรม เหมือนเซฟสูตรอาหารไว้ครั้งเดียว แล้วหยิบมาทำใหม่ได้เรื่อยๆ ไม่ต้องเขียนสูตรใหม่ทุกรอบ
- บล็อก `define function [name]` — ห่อกลุ่ม logic ไว้ด้วยกัน ตั้งชื่อ
- บล็อก `call function [name]` — เรียกใช้ฟังก์ชันที่นิยามไว้แล้ว
- **จุดที่ต้องเน้น:** ทำไมสำคัญ — ถ้า mission ต้องเช็คทั้งแบตและอุณหภูมิพร้อมกันในหลายจุดของโปรแกรม การมีฟังก์ชันทำให้ไม่ต้องลากบล็อกซ้ำก้อนเดิมหลายรอบ แก้ตรงเดียวจบ

## 4.3 บล็อกทั้งหมดที่ใช้ได้ (4 กลุ่ม)

ให้ยึดโครงเดียวกับที่ OBC ทำงานจริงในโมดูล 2 (รับข้อมูล → เก็บ/ตัดสินใจ → สั่งงาน) เพื่อให้ผู้เรียนรู้สึกว่ากำลัง "เขียนสมอง" ของสิ่งที่เพิ่งเรียนรู้จักไป ไม่ใช่บล็อกลอยๆ ที่ไม่เกี่ยวอะไรกับโมดูลก่อนหน้า

### 🔵 Input Blocks (บล็อกรับข้อมูล) — มาจากการ "อ่านค่า" ของแต่ละ subsystem
| บล็อก | อ่านค่าจากระบบไหน (ทวนโมดูล 2) | ชนิดข้อมูล | ตัวอย่างค่าที่ได้ |
|---|---|---|---|
| `battery level` | EPS | Number | เปอร์เซ็นต์แบตเตอรี่ (0-100%) |
| `sun sensor` | EPS/Payload | Boolean | ตรวจว่ากำลังโดนแสงอาทิตย์อยู่หรือไม่ |
| `ground command received` | COMM | String | คำสั่งที่พื้นโลกส่งขึ้นมา (uplink) |
| `in range of ground station` | COMM | Boolean | ตรวจว่ากำลังบินผ่านระยะสัญญาณสถานีภาคพื้นหรือไม่ |
| `temperature` | Payload/EPS | Number | อุณหภูมิปัจจุบัน (°C) |

### 🟣 Data Blocks (บล็อกจัดการข้อมูล) — ใหม่
| บล็อก | ทำหน้าที่ |
|---|---|
| `set variable [name] = [value]` | เก็บค่าไว้ในตัวแปรเพื่อใช้ทีหลัง |
| `pack data [...] → packet` | รวบค่าหลายตัวเป็น packet เดียวก่อนส่ง |
| `define function [name]` / `call function [name]` | ห่อ logic ไว้ใช้ซ้ำ |

### 🟡 Logic / Control Blocks (บล็อกตรรกะและควบคุมลำดับ)
- `if / else` (ซ้อนได้หลายชั้น) — ถ้าเงื่อนไขเป็นจริง ทำอย่างหนึ่ง ถ้าไม่จริง ทำอีกอย่างหนึ่ง
- เงื่อนไขเปรียบเทียบ เช่น `battery level < 20%` (ต้องเทียบชนิดข้อมูลให้ตรงกันตาม 4.2.1)
- `and / or` — รวมหลายเงื่อนไขเข้าด้วยกัน (เช่น "ได้รับคำสั่ง **และ** อยู่ในระยะสัญญาณ")
- `repeat forever` / `repeat every [X] seconds` — วนซ้ำ (ทวนจาก 4.2.3)

### 🟢 Output Blocks (บล็อกสั่งงาน) — คือคำสั่งที่ OBC ส่งไปให้ subsystem อื่นทำ
| บล็อก | สั่งไปที่ระบบไหน | ผลลัพธ์ |
|---|---|---|
| `deploy solar panel` | EPS | กางแผงโซลาร์เซลล์ |
| `enter safe mode` | ทุกระบบ | ลดการใช้พลังงานของ Payload ชั่วคราว |
| `capture image` | Payload | สั่งถ่ายภาพ/เก็บข้อมูล |
| `transmit data [packet]` | COMM | ส่ง downlink packet ข้อมูลลงพื้นโลก |
| `orient toward sun` | EPS/ADCS* | หมุนตัวดาวเทียมให้แผงโซลาร์รับแดดเต็มที่ |

*(ADCS = Attitude Determination and Control System หรือ "ระบบควบคุมทิศทาง" — เกริ่นสั้นๆ ตรงนี้ก็พอ เพราะพูดถึงแล้วในโมดูล 3 ตอนสนามแม่เหล็ก ไม่ต้องอธิบายซ้ำยาว)

## 4.4 ภารกิจ (Mission-based Progression)

หลักการ: **ทุก mission ต้อง "Run" แล้วเห็นผลจริงบน 3D CubeSat + mini dashboard** ไม่ใช่แค่ขึ้นเครื่องหมายถูก — ไล่ความซับซ้อนจาก block เดี่ยวๆ ไปจนถึงใช้ loop/variable/function/packet ครบทุก concept จาก 4.2

### Mission 1: First Light
- **โจทย์:** หลังแยกตัวจากจรวด ให้กางแผงโซลาร์เมื่อ sensor ตรวจพบแดด
- **บล็อกที่ต้องใช้:** `Input: sun sensor` → `Output: deploy solar panel`
- **Outcome ที่เห็น:** แผงโซลาร์บนโมเดล 3D กางออก + กราฟแบตเตอรี่บน dashboard เริ่มขึ้น
- **จุดสอน:** การเชื่อม input-output อย่างง่ายที่สุด ยังไม่มี logic เงื่อนไข

### Mission 2: Safe Mode (with Nested If/Else)
- **โจทย์:** เช็คระดับแบตแบบละเอียดขึ้น — ถ้าแบต **ต่ำกว่า 10%** ให้ปิด Payload ทั้งหมด, ถ้า **ต่ำกว่า 20%** (แต่ไม่ถึง 10%) ให้ลดพลังงานบางส่วน, นอกนั้นทำงานปกติ
- **บล็อกที่ต้องใช้:** `Input: battery level` → `Logic: if battery < 10%` → `Output: shutdown payload` → `else if battery < 20%` → `Output: enter safe mode` → `else: normal operation`
- **Outcome ที่เห็น:** โมเดล 3D มี 3 สถานะไฟที่ต่างกันชัดเจนตามระดับแบต ไม่ใช่แค่ 2 สถานะ
- **จุดสอน:** if/else ซ้อนหลายชั้น (4.2.2) — เห็นว่าการตัดสินใจจริงมักมีมากกว่า 2 ทางเลือก

### Mission 3: Continuous Monitoring (with Loop + Variable)
- **โจทย์:** ดาวเทียมต้องเช็คอุณหภูมิ **ทุกๆ 10 วินาที** ตลอดเวลา ไม่ใช่เช็คครั้งเดียวจบ และต้องจำค่าล่าสุดไว้เทียบกับรอบใหม่ว่าอุณหภูมิ "กำลังสูงขึ้น" หรือไม่
- **บล็อกที่ต้องใช้:** `Logic: repeat every 10 seconds` → ครอบ → `Input: temperature` → `Data: set variable lastTemp = temperature` (ในรอบแรก) → รอบถัดไปเทียบ `temperature > lastTemp` → `Output` ตามเงื่อนไข
- **Outcome ที่เห็น:** dashboard อัปเดตกราฟอุณหภูมิเป็นเส้นต่อเนื่องแบบ real-time แทนที่จะเป็นแค่ค่าเดียว ให้เห็นภาพว่า loop วิ่งอยู่จริง
- **จุดสอน:** Loop (4.2.3) และ Variable (4.2.4) — ปลูกฝังว่า OBC จริงไม่เคยหยุดทำงาน มันวนเช็คตลอดเวลา

### Mission 4: Photo Op (with Function + Packet)
- **โจทย์:** รับคำสั่งถ่ายภาพจากพื้นโลก แล้วต้องรวบข้อมูล (ภาพ + สถานะแบต + อุณหภูมิ ณ ขณะนั้น) เป็น packet เดียวก่อนส่งกลับ แต่ส่งได้เฉพาะตอนอยู่ในระยะสัญญาณเท่านั้น
- **บล็อกที่ต้องใช้:**
  - `define function checkCommWindow()` → คืนค่า `ground command received AND in range of ground station`
  - `Input: call function checkCommWindow()` → `Logic: if true` → `Output: capture image` → `Data: pack data [image, battery level, temperature] → packet` → `Output: transmit data [packet]`
- **Outcome ที่เห็น:** จำลอง animation downlink ส่ง packet กลับไปยัง ground station บนแผนที่/orbit view (เชื่อมกับ Orbit Playground ในโมดูล 1) พร้อมแสดง "เนื้อใน" ของ packet ที่ส่งไปให้เห็นว่ามีค่าอะไรอยู่ข้างในบ้าง
- **จุดสอน:** Function (4.2.5) และ Packet (4.2.4) — เห็นว่าการเรียกใช้ฟังก์ชันซ้ำและการรวบข้อมูลเป็น packet คือสิ่งที่ทำให้โปรแกรมสั้นลงและใกล้เคียงของจริงมากขึ้น

### Mission 5 (Capstone — ปลายเปิด)
- **โจทย์:** "อุณหภูมิของ Payload สูงเกินกำหนดระหว่างที่ loop กำลังเช็คอยู่ ควรทำอย่างไร?" — ไม่มีคำตอบตายตัวเดียว ผู้เรียนต้องผสมทุก concept ที่เรียนมา (loop, if/else, function, packet) เพื่อออกแบบพฤติกรรมของตัวเอง เช่น ปิด payload ชั่วคราว / หมุนตัวหนีแดด / เก็บค่าเป็น packet แล้วส่ง telemetry แจ้งพื้นโลกทันทีที่เข้าระยะสัญญาณ
- **บทบาทของ LAIKA:** ให้ feedback แบบ Socratic ไม่เฉลยตรงๆ เช่น "ถ้าปิด Payload อย่างเดียวโดยไม่แจ้งพื้นโลกเลย ทีมภาคพื้นจะรู้ได้ยังไงว่าเกิดอะไรขึ้น?" หรือ "ถ้าไม่ใช้ loop ครอบไว้ ดาวเทียมจะเช็คอุณหภูมิได้กี่ครั้ง?"

## 4.5 Interactive Mechanic

- Block editor แบบลากวาง (drag-and-drop) 4 สีตามกลุ่ม Input/Data/Logic/Output ต่อกันเป็น flow บนหน้าจอ รองรับการซ้อนบล็อก (nested if, บล็อกอยู่ใน loop) แบบมี indent ให้เห็นชัดเจน
- ปุ่ม **Run** จะ simulate ผลลัพธ์แบบ step-by-step ไม่ใช่กระโดดไปผลลัพธ์สุดท้ายทันที — ให้เห็น "ทีละ block ทำงาน" คล้าย debugger ง่ายๆ เพื่อสร้างความเข้าใจ sequence และเมื่อเจอบล็อก `repeat`/loop ให้ highlight วนซ้ำให้เห็นจริงๆ ว่ามันวน ไม่ใช่รันครั้งเดียวจบ (ใช้ speed control ให้ผู้เรียนเร่ง/ชะลอการวนได้ ไม่งั้นดูไม่ทันหรือน่าเบื่อเกินไป)
- ผลลัพธ์แสดงพร้อมกัน 2 จุด: (1) 3D CubeSat เปลี่ยนสถานะ (กางแผง/หรี่ไฟ/หมุนตัว) (2) mini telemetry dashboard อัปเดตค่าจริง (แบต, อุณหภูมิ, สถานะ COMM) — ให้ผู้เรียนเห็นว่าโค้ดกระทบ "ตัวเลขจริง" ไม่ใช่แค่ animation สวยๆ
- เมื่อมีการสร้าง/ส่ง packet (Mission 4) ให้เปิด panel เล็กๆ แสดง "เนื้อใน" packet เป็นก้อนข้อมูล (เช่น กล่อง JSON-like) ให้เห็นว่าค่าจาก sensor หลายตัวถูกรวบเข้าด้วยกันจริง

## 4.6 เกร็ดเทคนิคเบื้องหลังบล็อก (สำหรับความถูกต้อง — ใช้เป็น optional/advanced note ให้ LAIKA เปิดเผยเมื่อผู้เรียนถามลึกขึ้น)

เพื่อไม่ให้เนื้อหาความรู้ผิดเพี้ยนจากของจริง แม้จะย่อให้ง่ายด้วยบล็อก แต่หลักการเบื้องหลังควรอ้างอิงกับสถาปัตยกรรมจริงที่ CubeSat ใช้:

- **การสื่อสารภายในระหว่าง subsystem (ทวนจากโมดูล 2):** ในของจริง OBC ไม่ได้ "คุย" กับ EPS/COMM/Payload ผ่านสายลอยๆ แต่ผ่าน **บัสสื่อสารภายใน (internal bus)** มาตรฐาน เช่น **I2C** หรือ **CAN bus** และมักใช้โปรโตคอลเฉพาะทางอย่าง **CSP (CubeSat Space Protocol)** ซึ่งเป็นโปรโตคอลเครือข่ายน้ำหนักเบาที่ออกแบบมาสำหรับดาวเทียมเล็กโดยเฉพาะ ทำหน้าที่คล้าย "ที่อยู่ IP ย่อส่วน" ให้แต่ละ subsystem มีหมายเลขของตัวเองบนบัสเดียวกัน คล้ายกับที่บล็อก `Input`/`Output` ในบทเรียนนี้เป็นตัวแทนของการ "ขอข้อมูล" และ "สั่งงาน" ผ่านบัสจริงเหล่านี้แบบย่อ
- **`if battery < 20% → safe mode` ในของจริง** มักถูกเรียกว่า **watchdog logic** หรือ fault-detection routine ซึ่งเป็นส่วนสำคัญของ flight software (ซอฟต์แวร์ควบคุมการบิน) แทบทุกดาวเทียม ไม่ใช่แค่ตัวอย่างสมมติ
- **`repeat forever` ในของจริง** คือสิ่งที่เรียกว่า **main loop** ของ flight software — โปรแกรมควบคุมดาวเทียมแทบทุกดวงเขียนเป็นลูปไม่สิ้นสุดที่วนอ่านค่า sensor → ประมวลผล → สั่งงาน ซ้ำไปเรื่อยๆ ตลอดอายุภารกิจ ไม่ได้รันแค่ครั้งเดียวแล้วจบเหมือนสคริปต์ทั่วไป
- **`pack data → packet` ในของจริง** สอดคล้องกับการออกแบบ **telemetry frame/packet format** ที่มีโครงสร้างแน่นอน (เช่น header ระบุประเภทข้อมูล ตามด้วยค่าจริงเรียงกันตามตำแหน่งที่กำหนดไว้) เพื่อให้ทีมภาคพื้นแกะข้อมูลกลับได้ถูกต้อง ไม่ใช่ส่งค่าดิบๆ แบบสุ่ม
- **`transmit data` ในของจริง** ต้องผ่านการเข้ารหัสเป็นแพ็กเก็ตตามมาตรฐานการสื่อสาร (เช่น โปรโตคอลวิทยุสมัครเล่น AX.25 สำหรับ CubeSat หลายดวง) — บทเรียนนี้ตั้งใจไม่ลงรายละเอียดระดับนั้นเพราะเกินขอบเขตผู้เริ่มต้น แต่ถ้าผู้เรียนถามลึก ให้ LAIKA อธิบายว่ามีมาตรฐานจริงรองรับอยู่เบื้องหลัง ไม่ใช่การส่งข้อมูลลอยๆ

**หลักการเขียนบล็อกให้ทีม dev:** ชื่อบล็อกและ logic flow ในโมดูลนี้ควรตั้งชื่อให้สอดคล้อง terminology จริงที่ใช้ในวงการ (ตามตารางในหัวข้อ 4.3) เพื่อให้ผู้เรียนที่ไปต่อยอดเรียนเขียนโปรแกรม embedded จริงในอนาคตไม่ต้อง "เรียนใหม่" คำศัพท์ที่นี่ใช้ผิดจากของจริง

## Glossary สั้นๆ สำหรับโมดูลนี้
| คำศัพท์ | ความหมายแบบเข้าใจง่าย |
|---|---|
| Data Type (ชนิดข้อมูล) | ประเภทของค่าที่ตัวแปร/เซนเซอร์เก็บไว้ เช่น ตัวเลข, จริง-เท็จ, ข้อความ |
| Variable (ตัวแปร) | กล่องเก็บค่าไว้ใช้ในภายหลัง |
| Loop / Main Loop (การวนซ้ำ) | ส่วนของโปรแกรมที่ทำงานซ้ำไปเรื่อยๆ ไม่หยุด ตราบใดที่ดาวเทียมยังทำงานอยู่ |
| Function (ฟังก์ชัน) | กลุ่มคำสั่งที่ห่อไว้ใช้ชื่อเดียว เรียกใช้ซ้ำได้โดยไม่ต้องเขียนใหม่ |
| Packet (แพ็กเก็ตข้อมูล) | ก้อนข้อมูลที่รวบค่าหลายตัวเข้าด้วยกันก่อนส่ง มีโครงสร้างแน่นอนให้ปลายทางแกะออกได้ |
| Flight Software | ซอฟต์แวร์ที่ควบคุมการทำงานของดาวเทียมขณะบิน (สิ่งที่เรากำลังต่อบล็อกจำลองอยู่) |
| Watchdog / Fault-detection | ตรรกะที่คอยตรวจจับความผิดปกติแล้วสั่งรับมืออัตโนมัติ (เช่น safe mode) |
| Internal Bus (I2C / CAN) | เส้นทางสื่อสารมาตรฐานภายในดาวเทียมที่ subsystem ต่างๆ ใช้คุยกัน |
| CSP (CubeSat Space Protocol) | โปรโตคอลเครือข่ายน้ำหนักเบาที่ออกแบบเฉพาะสำหรับดาวเทียมเล็ก ใช้ส่งข้อมูลระหว่าง subsystem |
| Space Debris (ขยะอวกาศ) | วัตถุที่ลอยอยู่ในวงโคจรโดยไม่มีหน้าที่/ควบคุมไม่ได้อีกต่อไป |

## คำถามชวนคิดแบบ Socratic ที่ LAIKA ใช้ได้ระหว่างบทเรียน
- "ถ้าลืมต่อเงื่อนไข `else` ไว้ตอนแบตเตอรี่ปกติ จะเกิดอะไรขึ้นกับดาวเทียม?"
- "ทำไมการสั่ง `transmit data` ถึงต้องเช็ค `in range of ground station` ก่อนเสมอ ทั้งที่บล็อกสั่งได้เลยทันที?"
- "ถ้า OBC ไม่มีโปรแกรมสั่งไว้เลยแม้แต่บรรทัดเดียว ดาวเทียมจะกลายเป็นอะไร?"
- "ถ้าไม่มี `repeat forever` ครอบไว้ โปรแกรมเช็คอุณหภูมิของเราจะทำงานกี่ครั้งแล้วหยุด?"
- "ทำไมต้องรวบค่าเป็น packet ก่อนส่ง ทำไมส่งค่าทีละตัวแยกกันไม่ได้เหรอ?"
- "ถ้าเรามีจุดที่ต้องเช็คแบตอยู่ 3 จุดในโปรแกรม การมีฟังก์ชัน `checkBattery()` ช่วยอะไรได้บ้าง?"
